# Архитектура am-system

Система контроля позиции управляющей компании паевых фондов: учёт сделок,
построение позиций, переоценка, финансовый результат, метрики, денежная
позиция и лестница расчётов, контроль лимитов, сверка с брокером.

Документ описывает согласованную архитектуру. Решения по предметной области
с номерами вопросов — в [decisions.md](decisions.md), открытые вопросы —
в [open-questions.md](open-questions.md).

## 1. Принципы

**Ядро — детерминированный дневной ролл.**

```
состояние(портфель, D) = ролл( состояние(портфель, D−1),
                               события(D),           // сделки, операции с паями, расходы, купоны, погашения
                               рыночные данные(D),   // цены, фиксинги
                               версии инструментов(D) )
```

`ролл` — чистая функция без ввода-вывода. Из этого следуют пересчёт задним
числом, воспроизводимость, тестируемость и аудит.

**Пересчёт запускают три вида изменений:** правка сделок и операций, правка
рыночных данных за прошлую дату, новая версия инструмента. Деньги зависят от
рынка (ВМ, комиссии от СЧА), поэтому пересчитываются и они.

**Две оси дат.** По дате сделки — экономическая позиция (риск, переоценка,
P&L). По дате расчётов — что на счетах (деньги и бумаги на T, T+1, …). Купон
получает тот, у кого бумага на счёте на дату фиксации, — по расчётной оси.
Сверка с брокером тоже идёт по расчётной оси.

**Доверие = воспроизводимость + прослеживаемость + сверка с эталоном.**
Каждая цифра пересчитывается из сохранённых входов; у каждой оценки видно,
какая цена, версия инструмента и метод использованы; расчёты сверяются
с MOEX ISS и эталонными примерами пользователя.

**Не переусложнять.** Масштаб: ~10 портфелей, 5 пользователей, ~1000 сделок
в день, ~100 бумаг. Один PostgreSQL справляется с запасом. Сервисы без
состояния — ради отказоустойчивости и спокойных обновлений, а не ради
нагрузки.

## 2. Предметная модель (каркас)

- **Портфели** образуют ациклический граф. *Compound* содержит только
  портфели, *physical* — только сделки и обязан входить хотя бы в один
  compound. И compound, и physical могут входить в несколько compound.
- **Фонд (ПИФ)** — головной compound. У каждого physical ровно один
  фонд-предок; фонд не входит в другой фонд. Остальные compound —
  представления («все фонды», «книга трейдера»).
- **Агрегат compound** — сумма по множеству уникальных physical-потомков,
  а не по детям: иначе physical, входящий в compound двумя путями,
  посчитается дважды.
- **Счёт** — пара «денежный счёт + счёт депо» (депо может отсутствовать,
  например у счёта срочного рынка). Тип денежного счёта: брокерский или
  банковский. У пары есть признак рынков (фондовый, срочный, оба). Каждый
  physical привязан к одной паре; на одной паре может быть несколько
  physical. Лестница расчётов строится по счёту.
- **Казначейский physical** фонда — сюда проводятся операции уровня фонда:
  паи, вознаграждения, расходы.
- **Роли:** трейдинг, сопровождение, администратор. Админ видит всё и может
  всё. Доступ к портфелям выдаёт админ на compound; он распространяется на
  всех потомков.

## 3. Сервисы

| Сервис | Отвечает за | Владеет данными |
|---|---|---|
| `portfolio` | граф портфелей, фонды, счета, права пользователей | портфели, связи, счета, права |
| `refdata` | инструменты и версии, графики купонов/амортизаций/оферт, параметры флоатеров, календари, правила расчётов | справочники |
| `marketdata` | приём цен по API, ручной ввод, фиксинги, DEMA, выбор цены по правилу | временные ряды |
| `booking` | сделки, операции с паями и расходами, переводы, импорт; позиции, деньги, лестница расчётов, оценка, P&L, СЧА, комиссии; запрет правок в закрытом периоде | версии сделок и операций, дневные снапшоты |
| `reconciliation` | приём остатков от брокера и из банковской выписки, сопоставление, расхождения, закрытие дня по фонду | загруженные остатки, расхождения, закрытые дни |
| `limits` | лимиты, проверки по результатам расчёта, нарушения | лимиты, нарушения |
| `audit` | единый журнал действий пользователей | журнал (только дозапись) |

Общие библиотеки:

- `am-common` — настройки, проверка токенов и ролей, подключение к БД,
  фабрика приложения; позже — outbox и журналирование.
- `am-quant` — вся финансовая математика без ввода-вывода (НКД, YTM/YTP,
  спреды, дюрации, DEMA, позже OIS и кривые).

**Почему сделки и расчёт позиций — в одном сервисе.** Правка сделки
и пометка «позиции с даты D невалидны» должны происходить в одной
транзакции. Иначе появляется окно, когда сделка изменена, а позиции об этом
не знают. Внутри `booking` — два модуля с жёсткой границей и два типа
процессов: API и воркеры пересчёта.

**Почему запрет правок в закрытом периоде — в `booking`, а не
в `reconciliation`.** Проверка «день закрыт?» должна выполняться в той же
транзакции, что и правка сделки. `reconciliation` закрывает и открывает
дни, `booking` хранит границу и проверяет её.

## 4. Ключевые механизмы

**Пересчёт задним числом.** В `booking` таблица «грязных» портфелей
`(портфель, грязно_с_даты)`. Изменение входов ставит
`грязно_с = min(текущее, D)` в той же транзакции; внешние изменения
приходят событием. Воркер берёт портфель с блокировкой строки
(`FOR UPDATE SKIP LOCKED`), роллит дни от `грязно_с` до сегодня
и фиксирует результат. Один портфель никогда не считают два воркера;
разные портфели считаются параллельно; очередь переживает падение любого
компонента. Сделка за сегодня — пересчёт одного дня.

**Ролл по календарным дням.** Начисления по РЕПО и комиссиям идут
и в выходные; сделки — по торговому календарю Мосбиржи.

**История расчётов.** Замещённые снапшоты не удаляются, а помечаются
замещёнными — можно воспроизвести, что система показывала до исправления.

**Закрытие дня.** Строго подряд, по фонду целиком, после сверки всех счетов
фонда. Закрывает сопровождение; открывает заново только админ
с комментарием. Повторное открытие требует новой сверки.

**События между сервисами.** Transactional outbox: событие пишется в БД
сервиса в той же транзакции, что и изменение, затем публикуется в Redis
Streams. Потребители идемпотентны.

**Версионирование.** Сделки и операции неизменяемы: правка — новая версия,
удаление — версия «отменена». Инструменты — версии с датой начала действия.
Физически ничего не удаляется.

**Прослеживаемость.** Строка оценки хранит взятую цену и её источник,
версию инструмента, метод и ссылку на запуск расчёта.

**Аутентификация и авторизация.** Пользователи и роли — в Keycloak
(OIDC, Authorization Code + PKCE). Права на портфели — доменные данные
в `portfolio`. Сервис проверяет подпись JWT по ключам Keycloak, issuer,
audience (`am-api`) и срок; роли берёт из `realm_access.roles`. Источники
данных (рыночные данные, остатки брокера) — клиенты Keycloak
с client credentials и отдельной ролью.

**Журнал.** Действие пользователя пишется в outbox в той же транзакции,
что и изменение (кто, когда, что, было/стало), и доставляется в `audit`.

**Точность.** Суммы и количества — `Decimal` / `NUMERIC`. Доходности
и спреды подбираются численно и округляются по правилам методики.

## 5. Фронтенд

- **Shell** — вход через Keycloak, навигация, загрузка микрофронтендов.
- **Микрофронтенды** по доменам: администрирование, сделки, позиции
  и риски, рыночные данные, справочники, сверка, журнал. Каждый собирается
  и выкладывается отдельно.
- **Контракт** — пакет `@am/platform`: shell монтирует remote с props
  `{ session, basePath }`. Микрофронтенд не знает про Keycloak: он берёт
  токен у сессии.
- **Сборка** — Rsbuild + Module Federation 2.0. React — singleton.
  Адреса remote вычисляются при запуске в браузере, поэтому один образ shell
  работает на любом адресе.
- **Отказоустойчивость.** Если remote не загрузился, shell продолжает
  работать и показывает сообщение вместо раздела.

## 6. Инфраструктура

Всё приложение — на одном адресе за шлюзом Traefik:

| Путь | Куда |
|---|---|
| `/auth/...` | Keycloak |
| `/api/<сервис>/...` | сервис (префикс срезается) |
| `/mfe/<имя>/...` | статика микрофронтенда |
| `/...` | shell |

Браузеру не нужен CORS, токен не уходит на сторонние адреса. Маршруты —
в одном файле `infra/traefik/dynamic/routes.yml`.

**PostgreSQL:** база `keycloak` для Keycloak; база `am` для сервисов —
у каждого сервиса своя схема и своя роль, чужие схемы ему недоступны.
`search_path` выставляется на схему сервиса при соединении.

**Окружения.** Локально — `docker compose`. Прод — в облаке; рекомендация —
управляемый PostgreSQL провайдера (резервные копии, восстановление на
момент времени), сервисы и Keycloak — в контейнерах. Код получает адреса
через переменные окружения и не знает, где работает.

## 7. Порядок работ

0. **Каркас** — репозиторий, compose, Keycloak, шлюз, `am-common`, заготовка
   `portfolio`, shell и первый микрофронтенд, CI. *(сделано)*
1. `portfolio` + `audit` + outbox + админка и журнал: граф, фонды, счета,
   права. *(сделано, см. [design/01-portfolio-audit.md](design/01-portfolio-audit.md))*
2. `refdata`: инструменты, версии, календари, адаптер MOEX ISS.
   *(сделано, см. [design/02-refdata.md](design/02-refdata.md))*
3. `marketdata`: цены от скрипта пользователя по API, ручной ввод,
   OHLC и DEMA, правило выбора цены, переоценка внутри дня; НКД и номинал
   на дату из ISS (решения 60, 63–74). *(сделано, см. [design/03-marketdata.md](design/03-marketdata.md))*
4. `am-quant` для облигаций с фиксированным купоном и офертами — с эталонными
   тестами; вменённые спреды флоатеров и линкеров над RUONIA (решения 75–80);
   ставки RUONIA, ключевая, RUSFAR. *(сделано, см.
   [design/04-bond-analytics.md](design/04-bond-analytics.md))*
5. `booking`: облигационные сделки, операции с паями и расходами, переводы,
   импорт → позиции, лестница расчётов, пересчёт задним числом.
   Методика — [design/05-booking.md](design/05-booking.md). *(части 5.1
   и 5.2 сделаны: сделки, позиции по двум датам, деньги, ролл и пересчёт
   по фонду, операции фонда, переводы, лестница расчётов)*
6. Оценка, P&L, СЧА, комиссии.
7. РЕПО, флоатеры (с плоским прогнозом ставки), БПИФ — **это MVP**.
8. `reconciliation`: приёмник остатков, сверка, закрытие дня.
9. `limits`.
10. Второй этап: фьючерсы RUONIA и OIS, кривая RUONIA.

Для каждого расчётного этапа сначала пишется раздел методики в `docs/`,
пользователь его утверждает, затем пишется код.

## 8. Технические решения каркаса

| Решение | Почему |
|---|---|
| Python 3.13, FastAPI, SQLAlchemy 2 (async), Pydantic 2, uv workspace | стек задан; uv — один инструмент для окружения и lock-файла |
| PyJWT + собственный кэш JWKS | прозрачная проверка токена без «магии» адаптеров; ротация ключей Keycloak поддерживается |
| httpx2 как HTTP-клиент | преемник httpx (команда pydantic) с совместимым API; Starlette переводит на него TestClient |
| Префикс за шлюзом — `uvicorn --root-path` | параметр `root_path` в FastAPI устарел; префикс задаётся в команде запуска сервиса рядом с маршрутом шлюза |
| Traefik с файловыми маршрутами | маршруты видны в одном файле; не нужен доступ к Docker socket |
| Rsbuild вместо Vite | Module Federation 2.0 в экосистеме Rspack/Rsbuild поддерживается штатно |
| TypeScript 6.0 | TypeScript 7 (нативный компилятор) пока не везде поддержан инструментами |
| React Router 7 | стабильный декларативный API |
| Outbox и журнал — на шаге 1, а не в каркасе | их проверяет только живой потребитель (`audit`) |
| Тесты сервисов — с настоящим PostgreSQL (testcontainers) | моки БД не ловят ошибок SQL и прав |
| Общие помощники интерфейса — пакет `@am/ui`, собирается в каждый микрофронтенд | у помощников нет общего состояния, поэтому делить их во время работы, как React, не нужно; микрофронтенды остаются независимыми |
| Время — по Москве (`zoneinfo` + пакет `tzdata`) | биржа и пользователи живут по Москве; `tzdata` даёт базу часовых поясов и на Windows, и в slim-образе |
