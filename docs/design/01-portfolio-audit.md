# Шаг 1. Портфели, счета, доступы и журнал действий

Документ описывает, что делает шаг 1 и по каким правилам. Общая архитектура —
в [../architecture.md](../architecture.md), решения по предметной области —
в [../decisions.md](../decisions.md).

## Что входит

- **Сервис `portfolio`** — граф портфелей, фонды, счета, казначейский
  портфель фонда, права доступа пользователей.
- **Outbox в `am-common`** — надёжная доставка событий об изменениях.
- **Сервис `audit`** — единый журнал действий пользователей.
- **Админка** (`mfe-admin`) и **журнал** (`mfe-audit`) во фронтенде.

## Допущения шага

Пока вы не скажете иначе, работа идёт на этих допущениях:

| # | Допущение |
|---|---|
| A1 | Доступ выдаётся только на compound (фонд или представление) и распространяется на всех потомков. На physical доступ не выдаётся. |
| A2 | Список пользователей для выдачи доступов берётся из Keycloak: сервис `portfolio` читает его служебной учётной записью `am-portfolio` с правами `view-users` и `query-users` — только чтение пользователей. Роли читаются по каждому пользователю, поэтому доступ к настройкам realm не нужен. |
| A3 | Журнал действий видит только администратор. |
| A4 | Портфели и счета не удаляются. На этом шаге можно переименовать, перестроить связи и сменить счёт. Архивирование появится вместе со сделками. |
| A5 | Physical создаётся сразу со счётом своего фонда. Фонд у physical после создания не меняется. |
| A6 | У портфеля и счёта есть короткий уникальный код (например, `OPIF1-BONDS`) и название. |

## Модель

```
portfolio                      account (пара счетов)
├─ id, code, name              ├─ id, code, name
├─ kind: compound | physical   ├─ fund_id → портфель-фонд
├─ is_fund (только compound)   ├─ cash_kind: broker | bank
├─ account_id (только physical)├─ institution (брокер или банк)
└─ treasury_id (только фонд)   ├─ cash_account, depo_account (может не быть)
                               └─ markets: фондовый, срочный
portfolio_link (parent → child)
access_grant (пользователь → compound)
```

## Правила графа

Проверяются после **каждого** изменения на всём графе (он маленький —
десятки узлов). Изменения графа выполняются строго по одному: транзакция
берёт блокировку графа, поэтому два администратора не могут одновременно
нарушить правило с двух сторон.

| Код | Правило |
|---|---|
| `parent_not_compound` | Родителем может быть только compound. |
| `self_link` | Портфель не может входить сам в себя. |
| `cycle` | В графе нет циклов. |
| `physical_without_parent` | Physical входит хотя бы в один compound. |
| `physical_fund_count` | У physical ровно один фонд среди предков. |
| `fund_inside_fund` | Фонд не входит в другой фонд (ни прямо, ни через промежуточные compound). |
| `physical_without_account` | У physical есть пара счетов. |
| `account_of_other_fund` | Счёт physical принадлежит его фонду. |
| `treasury_not_in_fund` | Казначейский портфель фонда — physical этого фонда. |
| `account_not_fund` | Счёт принадлежит фонду, а не обычному compound. |
| `duplicate_code` | Коды портфелей и счетов уникальны (без учёта регистра). |
| `fund_not_compound`, `account_on_compound`, `treasury_on_non_fund` | Поля портфеля соответствуют его типу. |
| `grant_not_compound` | Доступ выдаётся только на compound. |

Нарушение — ответ API `422` с кодом правила и понятным сообщением; изменение
не применяется.

**Агрегаты и доступ.** Видимые пользователю портфели = выданные ему
compound и все их потомки. Админ видит всё.

## Outbox и журнал

1. Сервис в одной транзакции меняет данные и пишет событие в свою таблицу
   `outbox`: кто, когда, что сделал, было/стало.
2. Ретранслятор (фоновая задача сервиса) публикует неотправленные события
   в Redis Stream `am.events.<сервис>` и помечает их отправленными.
3. Сервис `audit` читает потоки в группе потребителей `audit`, сохраняет
   событие (повтор с тем же `event_id` игнорируется) и подтверждает
   сообщение. Не подтверждённое сообщение через 30 секунд забирается
   повторно.
4. Таблица журнала — только дозапись: триггер в БД запрещает `UPDATE`
   и `DELETE`.

Гарантия: событие не теряется и не появляется без изменения; повторная
доставка возможна и безвредна.

Если фоновая задача (ретранслятор или потребитель) остановилась из-за
ошибки, `/ready` сервиса отвечает `503`, и оркестратор перезапускает
процесс.

## API `portfolio` (под `/api/portfolio`)

| Метод | Путь | Кто | Что |
|---|---|---|---|
| GET | `/me` | все | пользователь, роли, доступные портфели |
| GET | `/portfolios` | все | видимые портфели со связями, фондом и счётом |
| POST | `/portfolios` | админ | создать фонд, compound или physical |
| PATCH | `/portfolios/{id}` | админ | изменить код или название |
| PUT/DELETE | `/portfolios/{parent}/children/{child}` | админ | включить/исключить портфель |
| PUT | `/portfolios/{id}/account` | админ | сменить счёт physical |
| PUT | `/funds/{id}/treasury` | админ | назначить казначейский портфель |
| GET | `/accounts` | все | счета видимых фондов |
| POST, PATCH | `/accounts`, `/accounts/{id}` | админ | создать/изменить счёт |
| GET | `/users` | админ | пользователи Keycloak с ролями и доступами |
| PUT/DELETE | `/users/{subject}/grants/{portfolio}` | админ | выдать/отозвать доступ |

## API `audit` (под `/api/audit`)

| Метод | Путь | Кто | Что |
|---|---|---|---|
| GET | `/events` | админ | события журнала, новые сверху, с фильтрами и постраничной загрузкой |

## Миграции БД

Схема каждого сервиса описывается миграциями Alembic, написанными вручную.
Сервис применяет их при старте (под advisory-блокировкой, чтобы реплики
не мешали друг другу). Тест сверяет модель в коде с базой после миграций —
расхождение ловится до выкладки.
